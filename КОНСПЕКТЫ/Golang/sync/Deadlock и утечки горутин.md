### Deadlock (взаимная блокировка)

Состояние, когда горутины **ждут друг друга** и никто не может продолжить.
**Если заблокированы все горутины**, рантайм это обнаруживает и падает:

```
fatal error: all goroutines are asleep - deadlock!
```

Это `fatal error`, перехватить через `recover` нельзя. Но если хотя бы одна горутина жива (например, HTTP-сервер или таймер), рантайм deadlock **не заметит**, и часть программы молча зависнет.

#### Типичные причины

**1. Отправка или получение в канале без пары:**

```go
ch := make(chan int)
ch <- 1 // никто не читает
```

**2. Взаимная блокировка мьютексов (неправильный порядок):**

```go
// горутина 1: Lock(a); Lock(b)
// горутина 2: Lock(b); Lock(a)
```

**3. Повторный `Lock` в той же горутине** (мьютекс не рекурсивный), в том числе через вызов другого метода, который тоже берёт блокировку.
**4. Неверное использование `WaitGroup`:** `Wait` ждёт, но `Done` не вызывается (из-за раннего `return` без `defer`, паники или лишнего `Add`).
**5. Не закрыт канал при `range`:** цикл ждёт новых значений вечно.
**6. `RLock` + `Lock`** одной горутины (апгрейд читающей блокировки).
**7. `once.Do` внутри `once.Do`.**

#### Как избегать

- **Единый порядок захвата** нескольких мьютексов во всём коде.
- `defer mu.Unlock()` сразу после `Lock()`.
- Не вызывать неизвестный внешний код (колбэки) под мьютексом.
- Минимизировать критические секции и вложенные блокировки.
- Для каналов: определить, **кто владелец и кто закрывает**, использовать `select` с `ctx.Done()` или таймаутом.
- `defer wg.Done()` первой строкой горутины.
- Использовать `TryLock`/таймауты только в особых случаях, обычно это признак проблем в дизайне.

#### Как диагностировать

- Дамп всех горутин: `SIGQUIT` (`kill -QUIT <pid>`) или `Ctrl+\` печатает стеки всех горутин, видно, кто на чём заблокирован (`chan send`, `semacquire`, `sync.Mutex.Lock`).
- `pprof`: `/debug/pprof/goroutine?debug=2`.
- Тесты с `-timeout`, чтобы зависший тест падал со стеками.

### Утечки горутин (goroutine leak)

Горутина **никогда не завершается**, хотя её результат уже не нужен. Она держит стек, ссылки на объекты (не освобождаются GC) и ресурсы. Число горутин растёт, память утекает, сервис деградирует.

#### Типичные причины

**1. Отправка в канал без получателя:**
```go
func fetch() int {
    ch := make(chan int)
    go func() { ch <- compute() }() // зависнет, если никто не прочитает
    select {
    case v := <-ch:
        return v
    case <-time.After(time.Second):
        return -1 // вышли по таймауту, горутина осталась висеть
    }
}
```

Исправление: буферизованный канал `make(chan int, 1)`, тогда отправка завершится, или `ctx` в горутине.

**2. Чтение из канала, который никто не закрывает:**
```go
go func() {
    for v := range ch { handle(v) } // ждёт вечно, если ch не закрыт
}()
```
**3. Горутина не слушает `ctx.Done()`:** бесконечный цикл или блокирующий вызов без отмены.
**4. Забытый `Ticker` / вечный `select {}`** без выхода.
**5. HTTP-запросы без таймаута**, `resp.Body` не закрыт.
**6. Блокировка на мьютексе или `WaitGroup`**, которые никогда не освободятся.

#### Как избегать
- **У каждой горутины должен быть понятный способ завершения** (закрытие канала, `ctx.Done()`, возврат из функции). Перед `go` задайте себе вопрос: «Кто и когда её остановит?»
- Передавать `ctx` и проверять `ctx.Done()` в каждом блокирующем `select`.
- Результирующие каналы делать буферизованными (на размер числа отправителей), если получатель может уйти раньше.
- Закрывает канал **владелец-отправитель**, а `defer close(ch)` ставят в горутине-продюсере.
- Использовать `errgroup` с контекстом: при ошибке остальные получают отмену.
- Останавливать `Ticker` и `Timer` (`defer t.Stop()`).
- Задавать таймауты в `http.Client`, `database/sql` и сетевых вызовах.
- Контролировать **graceful shutdown**: ждать завершения горутин через `WaitGroup`.

#### Как обнаружить
- Метрика `runtime.NumGoroutine()`: если число постоянно растёт, это утечка.
- `pprof`: `go tool pprof http://host/debug/pprof/goroutine`, смотрите, где скапливаются горутины.
- В тестах: библиотека **`go.uber.org/goleak`** (`goleak.VerifyNone(t)`) падает, если после теста остались живые горутины. В Go 1.24 экспериментально появился профиль `goroutineleak` в `runtime/pprof`.

### Livelock и starvation (коротко)
- **Livelock**: горутины активно работают, но не продвигаются (постоянно уступают друг другу).
- **Starvation**: горутина долго не получает доступ к ресурсу (например, писатель при множестве читателей, хотя `RWMutex` от этого защищён).
