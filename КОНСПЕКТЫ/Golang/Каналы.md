Каналы в Go - абстракция реализованная поверх общей памяти,  для общения между горутинами, буфер каналов лежит в куче где элементы извлекаются в порядке отправки(FIFO)

**Канал** это типизированная труба для передачи значений между горутинами. Основа модели CSP: «не общайтесь через разделяемую память, делитесь памятью через общение».

Канал это ссылочный тип, zero value `nil`. Каналы потокобезопасны, синхронизировать доступ к ним мьютексом не нужно.

### Небуферизованный канал

`make(chan T)`, ёмкость 0. Отправка и получение **синхронны**: отправитель блокируется, пока кто-то не примет значение, а получатель блокируется, пока кто-то не отправит. Это точка встречи (rendezvous) двух горутин.

Как каналы применяют на практике
1) Сигнал готовности/завершения
2) как воркер пул
3) backpressure(ограничение скорости)
4) таймауты/отмена
5) Graceful shutdown

### Небуферизованный канал

`make(chan T)`, ёмкость 0. Отправка и получение **синхронны**: отправитель блокируется, пока кто-то не примет значение, а получатель блокируется, пока кто-то не отправит. Это точка встречи (rendezvous) двух горутин.

```go
ch := make(chan string)

go func() { ch <- "hello" }() // блокируется до получения

fmt.Println(<-ch) // получили, обе горутины продолжили
```

Если в одной горутине сделать `ch <- 1` без параллельного получателя, будет deadlock:

```go
ch := make(chan int)
ch <- 1 // fatal error: all goroutines are asleep - deadlock!
```

Гарантия: когда отправка завершилась, значение **уже получено**. Поэтому небуферизованные каналы удобны для синхронизации.

### Буферизованный канал

`make(chan T, n)`. Внутри очередь на `n` элементов.

- Отправка блокируется, только если буфер **полон**.
- Получение блокируется, только если буфер **пуст**.

```go
ch := make(chan int, 2)
ch <- 1
ch <- 2
// ch <- 3 заблокировалась бы: буфер полон
fmt.Println(<-ch, <-ch) // 1 2 (порядок FIFO)
```

`len(ch)` число элементов в буфере, `cap(ch)` ёмкость. Использовать их для логики синхронизации нельзя: значение устаревает сразу после чтения.

**Применение:** сглаживание всплесков, очередь заданий для воркеров, семафор (`chan struct{}` ёмкости N), результат горутины без блокировки отправителя (`make(chan Result, 1)`, чтобы горутина не утекла, если никто не прочитает).

**Ловушка:** буфер не лечит неверный дизайн. Если продюсер быстрее консьюмера, буфер рано или поздно заполнится, и всё равно придётся решать вопрос обратного давления.

|                                            | Небуферизованный                   | Буферизованный          |
| ------------------------------------------ | ---------------------------------- | ----------------------- |
| Отправка блокируется                       | пока нет получателя                | пока буфер полон        |
| Получение блокируется                      | пока нет отправителя               | пока буфер пуст         |
| Гарантия доставки при возврате из отправки | значение получено                  | значение лишь в очереди |
| Типичное применение                        | синхронизация, передача управления | очереди, пулы, семафоры |

### Закрытие канала

```go
close(ch)
```

Закрытие означает **«больше значений отправлено не будет»**. Это сигнал получателям, а не освобождение ресурса: закрывать каждый канал не обязательно, сборщик мусора уберёт его сам.

**Правила:**

- Закрывает **отправитель** (владелец канала), а не получатель.
- `close` закрытого канала вызывает **панику**.
- `close(nil)` вызывает **панику**.
- **Отправка** в закрытый канал вызывает **панику**.
- Определить, закрыт ли канал, без чтения нельзя (проверки `isClosed` нет и она была бы гонкой).
### Чтение из закрытого канала

1. Если в буфере остались значения, они **выдаются по порядку** как обычно.
2. Когда буфер опустел, получение **не блокируется** и немедленно возвращает **zero value** типа с `ok == false`.

```go
ch := make(chan int, 2)
ch <- 1
ch <- 2
close(ch)

v, ok := <-ch // 1, true
v, ok = <-ch  // 2, true
v, ok = <-ch  // 0, false: закрыт и пуст
v, ok = <-ch  // 0, false: так будет всегда
```

Без `ok` не отличить закрытый канал от настоящего нуля. Поэтому либо проверяют `ok`, либо используют `range`.

### range по каналу

`range` читает значения до закрытия канала и затем выходит из цикла:

```go
go func() {
    defer close(ch)
    for i := 0; i < 3; i++ {
        ch <- i
    }
}()

for v := range ch { // завершится после close
    fmt.Println(v)
}
```

Если канал **не закрыть**, а `range` ждёт, получится deadlock или утечка горутины.
`range` по каналу читает все значения, которые остались в буфере, и завершается только когда канал **закрыт и пуст**.
### nil-канал

- Отправка и получение блокируются **навсегда**.
- `close(nil)` паника.

Это используют намеренно в `select`: присвоив канал `nil`, вы «отключаете» ветку.

### Направленные каналы

```go
func producer(out chan<- int) { out <- 1 }   // только отправка
func consumer(in <-chan int)  { <-in }       // только получение
```

Компилятор не даст нарушить направление. Закрывать можно только канал, доступный для отправки (`chan<-` или двунаправленный), закрыть `<-chan` нельзя. Это закрепляет правило «закрывает отправитель».

### Ловушки

- **Утечка горутины:** отправитель заблокирован на канале, из которого никто не читает.
- **Deadlock:** все горутины спят на каналах.
- **Закрытие со стороны получателя** может привести к панике у отправителя.
- **Отправка в закрытый канал** паника, поэтому с несколькими отправителями нужна координация.
- **Чтение zero value** из закрытого канала принимают за реальные данные, если не проверять `ok`.
- **Копирование:** канал это ссылка, передача в функцию не копирует буфер.
**Несколько отправителей:** закрывать канал должен кто-то один, иначе паника. Обычно отдельная горутина ждёт `WaitGroup` и закрывает:

```go
go func() {
    wg.Wait()
    close(results)
}()
```
