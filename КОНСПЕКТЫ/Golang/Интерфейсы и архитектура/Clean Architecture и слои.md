### Идея слоёв

Разделение ответственности: каждый слой делает своё дело и знает только о соседнем.

```
HTTP-запрос
    ↓
┌──────────────┐
│   handler    │  транспорт: разбор запроса, валидация формата, ответ
├──────────────┤
│   service    │  бизнес-логика, правила, транзакции
├──────────────┤
│  repository  │  доступ к данным (БД, кэш, внешний API)
└──────────────┘
    ↓
   БД
```

#### Handler (transport / controller)

- Разбирает входящий запрос (JSON, параметры, заголовки), проверяет формат.
- Вызывает сервис.
- Преобразует результат или ошибку в ответ (статус-код, тело).
- **Бизнес-логики нет.**

```go
func (h *Handler) GetUser(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.Atoi(r.PathValue("id"))
    if err != nil {
        http.Error(w, "bad id", http.StatusBadRequest)
        return
    }

    u, err := h.svc.GetUser(r.Context(), id)
    switch {
    case errors.Is(err, domain.ErrNotFound):
        http.Error(w, "not found", http.StatusNotFound)
        return
    case err != nil:
        h.log.Error("get user", "err", err)
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }

    json.NewEncoder(w).Encode(toResponse(u))
}
```

#### Service (usecase / business logic)

- Реализует правила предметной области и сценарии: «зарегистрировать пользователя», «перевести деньги».
- Оркестрирует репозитории и внешние клиенты.
- Управляет транзакциями.
- **Ничего не знает про HTTP и SQL.**

```go
type UserRepo interface { // интерфейс у потребителя
    Get(ctx context.Context, id int) (*domain.User, error)
}

type Service struct{ repo UserRepo }

func (s *Service) GetUser(ctx context.Context, id int) (*domain.User, error) {
    u, err := s.repo.Get(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("get user %d: %w", id, err)
    }
    return u, nil
}
```

#### Repository (storage / data access)

- Выполняет запросы к БД и преобразует строки в доменные объекты.
- Прячет детали хранилища (SQL, драйвер).
- Переводит ошибки хранилища в доменные (`sql.ErrNoRows` → `domain.ErrNotFound`).

```go
func (r *UserRepo) Get(ctx context.Context, id int) (*domain.User, error) {
    var u domain.User
    err := r.db.QueryRowContext(ctx,
        "SELECT id, name FROM users WHERE id = $1", id).Scan(&u.ID, &u.Name)
    if errors.Is(err, sql.ErrNoRows) {
        return nil, domain.ErrNotFound
    }
    return &u, err
}
```

### Clean Architecture (Роберт Мартин)

Развитие той же идеи: код делится на концентрические круги, и **зависимости направлены только внутрь**, к бизнес-правилам.

```
 ┌──────────────────────────────────────────┐
 │ Frameworks & Drivers (HTTP, БД, брокер)  │
 │  ┌────────────────────────────────────┐  │
 │  │ Interface adapters (handler, repo) │  │
 │  │  ┌──────────────────────────────┐  │  │
 │  │  │ Use cases (service)          │  │  │
 │  │  │  ┌────────────────────────┐  │  │  │
 │  │  │  │ Entities (domain)      │  │  │  │
 │  │  │  └────────────────────────┘  │  │  │
 │  │  └──────────────────────────────┘  │  │
 │  └────────────────────────────────────┘  │
 └──────────────────────────────────────────┘
     зависимости направлены к центру
```

**Ключевое правило (Dependency Rule):** внутренние слои ничего не знают о внешних. Домен не импортирует `net/http`, `database/sql` или конкретный драйвер.

**Как это достигается в Go:** **инверсия зависимостей через интерфейсы**. Сервис объявляет интерфейс репозитория (у потребителя), а реализация в слое инфраструктуры его удовлетворяет. Во время выполнения `service` вызывает `repository`, но на уровне импортов `repository` зависит от `domain`, а не наоборот. Сборка всего вместе происходит в `main`.

Пример структуры:

```
internal/
├── domain/              # сущности и ошибки, без внешних зависимостей
│   ├── user.go
│   └── errors.go
├── service/             # use cases, интерфейсы зависимостей
│   └── user.go
├── repository/
│   └── postgres/        # реализация интерфейсов хранилища
│       └── user.go
└── transport/
    └── http/            # handlers, роутинг, DTO
        └── user.go
```

### Практические правила

- **Отдельные модели для слоёв.** DTO запроса/ответа (handler), доменная сущность (service), модель хранения (repository, с тегами `db`). Не тащите `json`/`db`-теги в домен. Маппинг между ними выглядит многословно, но развязывает слои.
- **Ошибки:** репозиторий возвращает доменные ошибки, handler переводит их в HTTP-статусы. Верхние слои не должны знать `sql.ErrNoRows`.
- **`context.Context`** передаётся через все слои первым аргументом.
- **Транзакции** обычно охватывают несколько операций репозитория, поэтому управляются на уровне сервиса (через интерфейс вроде `TxManager` или передачу `tx` через контекст/параметр).
- **Тестирование:** сервис тестируется с fake/mock репозиторием без БД и HTTP, handler через `httptest`, репозиторий интеграционными тестами с реальной БД.
- **Слои не пропускают друг друга:** handler не обращается к репозиторию напрямую.

### Когда это перебор

- Для маленького CRUD-сервиса три слоя с интерфейсами и маппингом дают много кода без выгоды (в Go критикуют «Java-style» архитектуру). Начинайте с минимума, добавляйте слои, когда появляется реальная логика.
- Интерфейс «на каждый сервис и репозиторий» без второй реализации и без нужды в моках это лишняя абстракция.
- Идеальное разделение не самоцель: цель в тестируемости и возможности менять инфраструктуру, не трогая бизнес-логику.

Альтернативы и родственные подходы: **Hexagonal Architecture (Ports & Adapters)** с теми же идеями, **DDD** для сложных предметных областей, **package by feature** (группировка по функциональности вместо слоёв).
