В Go нет обязательной структуры. Есть **неформальный стандарт** (golang-standards/project-layout), который широко используется, хотя не является официальным. Команда Go рекомендует начинать с простого и усложнять по мере роста.

### Типичная раскладка

```
myapp/
├── cmd/
│   ├── api/
│   │   └── main.go        # точка входа HTTP-сервиса
│   └── worker/
│       └── main.go        # точка входа воркера
├── internal/
│   ├── config/
│   ├── domain/
│   ├── service/
│   ├── repository/
│   └── transport/http/
├── pkg/                   # публичные переиспользуемые пакеты (опционально)
├── migrations/
├── api/                   # OpenAPI, proto-файлы
├── go.mod
└── go.sum
```

### `cmd/`

Точки входа приложения: по одной директории на каждый исполняемый файл (`cmd/api`, `cmd/worker`, `cmd/migrate`). Имя директории становится именем бинарника.

```bash
go build -o bin/api ./cmd/api
```

**Правило:** `main.go` тонкий. Он читает конфиг, собирает зависимости (composition root), запускает приложение и обрабатывает сигналы. Бизнес-логики в нём нет.

### `internal/`

Специальная директория, которую **обеспечивает сам компилятор**: пакеты внутри `internal/` можно импортировать только из кода, находящегося **в родительском каталоге `internal` и его поддереве**.

```
github.com/me/myapp/internal/service   // доступен внутри github.com/me/myapp/...
```

Любой другой модуль, попытавшись импортировать `github.com/me/myapp/internal/service`, получит ошибку компиляции:

```
use of internal package github.com/me/myapp/internal/service not allowed
```

**Зачем нужен:**

- **Скрыть реализацию.** Всё, что в `internal`, не является публичным API модуля. Внешние пользователи не могут от него зависеть.
- **Свобода рефакторинга.** Меняете, переименовываете и удаляете код без соблюдения обратной совместимости и без мажорных версий.
- **Чёткая граница**: публично только то, что вы осознанно вынесли наружу.

`internal` может лежать на любом уровне: `internal/` в корне закрывает пакет от внешних модулей, а `pkg/foo/internal/` закрывает его от остальных пакетов, кроме `pkg/foo` и его потомков.

Для приложения (не библиотеки) почти весь код кладут в `internal/`: делиться им всё равно не с кем.

### `pkg/`

Публичный код, который можно импортировать из других проектов.

**Спорный каталог.** Критика:

- Лишний уровень вложенности в импортах.
- Часто в него складывают всё подряд.
- Для приложения он бессмысленен: никто снаружи ваш код не импортирует.
- Многие крупные проекты обходятся без него (стандартная библиотека, Kubernetes использует `staging`, не `pkg` в этом смысле).

**Рекомендация:** для сервисов `pkg/` не нужен. Для библиотеки публичные пакеты проще держать прямо в корне модуля, а детали прятать в `internal/`.

### Прочие каталоги

|Каталог|Назначение|
|---|---|
|`api/`|спецификации (OpenAPI, `.proto`)|
|`migrations/`|SQL-миграции|
|`configs/`|примеры конфигов|
|`scripts/`|вспомогательные скрипты|
|`deployments/`|Dockerfile, Helm, compose|
|`testdata/`|данные для тестов (игнорируется сборкой)|
|`vendor/`|зависимости (если используется vendoring)|

### Практические советы

- **Начинайте просто.** Для маленького сервиса достаточно `main.go` в корне плюс пара пакетов. Раскладывайте по каталогам, когда это становится нужно.
- **Пакеты называйте по назначению**, а не по типу (`user`, `billing`, а не `models`, `utils`, `helpers`). Имя короткое, в нижнем регистре, без подчёркиваний.
- **Избегайте циклических импортов** (компилятор их запрещает): они сигнал, что границы пакетов выбраны неверно.
- **Два подхода к группировке:** по слоям (`handler/`, `service/`, `repository/`) или по предметным областям (`user/`, `order/`, внутри каждой свои слои). Для больших проектов второй вариант масштабируется лучше.
