**Идиоматичный Go: на стороне потребителя** (пакета, который использует зависимость).

Причина: в Go интерфейсы удовлетворяются **неявно** (структурная типизация). Поставщику не нужно знать, что его тип подходит под чей-то интерфейс, а потребитель описывает ровно то, что использует.

```go
// пакет postgres (поставщик): только структура, без интерфейсов
package postgres

type UserRepo struct{ db *sql.DB }

func (r *UserRepo) Get(ctx context.Context, id int) (*User, error) { ... }
func (r *UserRepo) Save(ctx context.Context, u *User) error { ... }
func (r *UserRepo) Delete(ctx context.Context, id int) error { ... }
func (r *UserRepo) List(ctx context.Context) ([]User, error) { ... }
```

```go
// пакет billing (потребитель): интерфейс только с тем, что нужно ему
package billing

type userGetter interface {
    Get(ctx context.Context, id int) (*User, error)
}

type Service struct{ users userGetter }

func NewService(u userGetter) *Service { return &Service{users: u} }
```

`*postgres.UserRepo` подходит под `userGetter`, хотя `postgres` о нём ничего не знает. Каждый потребитель берёт только нужные методы, поэтому интерфейсы маленькие (`Interface Segregation`), а зависимости между пакетами минимальны (нет импорта пакета ради интерфейса).

### Противоположный подход: у поставщика

В Java/C# интерфейс обычно лежит рядом с реализацией. В Go это антипаттерн, когда интерфейс огромный («репозиторий на 20 методов») и объявлен вместе с единственной реализацией: потребитель тянет за собой лишнее, а мок приходится писать на все методы.

### Исключения, когда интерфейс у поставщика

- **Стандартные контракты**, которые определяют все: `io.Reader`, `http.Handler`, `sort.Interface`, `database/sql/driver.Driver`. Интерфейс и есть контракт.
- **Плагинная архитектура:** пакет определяет интерфейс, который должны реализовать внешние сторонние типы.
- **Несколько реализаций с общим поведением** в одном модуле (драйверы, хранилища), где интерфейс описывает общий контракт. Его всё равно делают маленьким.
- **Публичная библиотека**, где вы хотите гарантировать API.

### Практика

- Интерфейс из 1-3 методов, имя часто по действию (`Reader`, `Getter`, `Notifier`).
- Объявляйте его там, где используется, даже если он дублирует интерфейс в соседнем пакете: небольшое дублирование лучше связности.
- В структуре с чистой архитектурой интерфейс репозитория лежит в **слое сервиса/домена**, а реализация в слое инфраструктуры (`postgres`). Зависимость направлена к домену, а не наоборот.
- Компиляторная проверка реализации у поставщика, если хотите явную гарантию: `var _ billing.UserGetter = (*UserRepo)(nil)` (но тогда появляется импорт).
