### WithCancelCause (Go 1.20)

Обычный `cancel()` даёт лишь `context.Canceled`, причину не узнать. `WithCancelCause` позволяет передать **конкретную ошибку-причину**.

```go
ctx, cancel := context.WithCancelCause(parent)

cancel(errors.New("upstream unavailable")) // отмена с причиной

fmt.Println(ctx.Err())            // context canceled  (Err() остаётся прежним)
fmt.Println(context.Cause(ctx))   // upstream unavailable
```

- `cancel(nil)` эквивалентно `context.Canceled` в качестве причины.
- `context.Cause(ctx)` возвращает причину. Если отмены не было или контекст создан обычным способом, возвращает `ctx.Err()`.
- Причина фиксируется **первой** отменой, последующие игнорируются.
- Работает и для таймаутов (Go 1.21): `WithTimeoutCause(parent, d, cause)` и `WithDeadlineCause`, тогда `Cause` при истечении времени вернёт вашу ошибку вместо безликого `DeadlineExceeded`.

Применение: понять, **почему** операция остановлена (первая упавшая подзадача, потеря соединения, ручная остановка), и вернуть осмысленную ошибку, а не просто «context canceled».

### AfterFunc (Go 1.21)

Регистрирует функцию, которая **запустится в отдельной горутине после отмены контекста** (или сразу, если он уже отменён).

```go
stop := context.AfterFunc(ctx, func() {
    log.Println("ctx done, cleaning up")
    conn.Close()
})

// если очистка больше не нужна:
if stop() {
    // функцию успели отменить, она не будет вызвана
}
```
- Возвращает функцию `stop() bool`: `true`, если удалось предотвратить запуск; `false`, если функция уже запущена (или запускалась).
- Каждый вызов `AfterFunc` независим, несколько функций на один контекст допустимы.
- `stop` не ждёт завершения уже запущенной функции. Если нужно дождаться, синхронизируйтесь сами (например, `WaitGroup` или канал).
Типичный случай: **связать отмену контекста с API, которое контекст не понимает**. Например, прервать блокирующую операцию, вызвав `conn.SetDeadline(time.Now())` или `cond.Broadcast()`, когда `ctx` отменён.
