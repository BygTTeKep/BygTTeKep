**Структурное логирование** это запись событий не в виде свободного текста, а как **набор именованных полей** (обычно JSON или `key=value`).

Сравните:

```
// неструктурно
2026/09/30 10:00:00 user 42 failed to pay 100 USD: card declined

// структурно
{"time":"2026-09-30T10:00:00Z","level":"ERROR","msg":"payment failed","user_id":42,"amount":100,"currency":"USD","reason":"card declined"}
```

### Зачем оно нужно

- **Машиночитаемость.** Логи можно фильтровать и агрегировать без регулярных выражений: `level=ERROR AND user_id=42`.
- **Поиск и аналитика.** Системы вроде Elasticsearch, Loki, Datadog индексируют поля: можно посчитать ошибки по `reason`, построить график по `amount`.
- **Стабильный формат.** Сообщение остаётся постоянным (`"payment failed"`), меняются только поля. Проще алертинг и группировка одинаковых событий.
- **Контекст.** Общие поля (`request_id`, `service`, `version`) добавляются один раз через `logger.With(...)` и попадают в каждую запись.
- **Корреляция.** По `trace_id` можно собрать все записи одного запроса через несколько сервисов.
- **Меньше ошибок форматирования.** Не нужно склеивать строки вручную.

### Хорошие практики

- Используйте **единый набор имён полей** (`user_id`, а не то `userId`, то `uid`).
- Сообщение делайте **коротким и постоянным**, переменные данные выносите в поля.
- Не кладите в лог большие объекты целиком и чувствительные данные.
- Для локальной разработки удобнее text-handler, в проде JSON.
