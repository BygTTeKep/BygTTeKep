Это параметр через который метод привязывается к типу 

**Receiver** это параметр, через который метод привязывается к типу.

```go
func (u User) Name() string      { return u.name }  // value receiver: работает с копией
func (u *User) SetName(n string) { u.name = n }     // pointer receiver: работает с оригиналом
```

### Разница

- **Value receiver** получает **копию** значения. Изменения внутри метода снаружи не видны.
- **Pointer receiver** получает **адрес**. Метод может менять оригинал, копирования нет.

```go
type Counter struct{ n int }

func (c Counter) IncVal()  { c.n++ }  // меняет копию
func (c *Counter) IncPtr() { c.n++ }  // меняет оригинал

c := Counter{}
c.IncVal(); fmt.Println(c.n) // 0
c.IncPtr(); fmt.Println(c.n) // 1
```

Вызов удобен: если `c` адресуемая переменная, `c.IncPtr()` компилятор сам превращает в `(&c).IncPtr()`.

### Когда использовать pointer receiver

- Метод **меняет состояние** структуры.
- Структура **большая**, копировать дорого.
- Структура содержит **`sync.Mutex`, `sync.WaitGroup`** и другие типы, которые нельзя копировать.
- **Единообразие**: если хотя бы один метод типа с pointer receiver, остальные тоже делают pointer receiver. Смешивать не рекомендуется.

### Когда использовать value receiver

- Маленькие неизменяемые типы: `time.Time`, `Point{X, Y}`, обёртки над примитивами.
- Типы на основе map, func, chan (они и так ссылочные).
- Нужна гарантия, что метод **ничего не меняет**.
- Небольшие слайсы-типы, которые метод не переприсваивает.

### Method sets и интерфейсы

Это самое частое место вопросов на собеседовании.

| Тип  | Какие методы входят в method set    |
| ---- | ----------------------------------- |
| `T`  | только с receiver `T`               |
| `*T` | и с receiver `T`, и с receiver `*T` |

Следствие: **значение `T` не реализует интерфейс, если методы объявлены с pointer receiver.**

```go
type Speaker interface{ Speak() string }

type Dog struct{}
func (d *Dog) Speak() string { return "woof" }

var s Speaker = &Dog{} // ок
var s2 Speaker = Dog{} // ошибка: Dog does not implement Speaker (Speak has pointer receiver)
```

Обратное работает: если метод с value receiver, интерфейс реализуют и `T`, и `*T`.

### Почему так сделано

Когда ты кладёшь `Dog{}` в интерфейс, туда копируется значение. Это значение внутри интерфейса **не адресуемо**: взять его адрес, чтобы вызвать метод с pointer receiver, нельзя. А если бы Go молча создавал временную копию и вызывал метод на ней, любые изменения внутри метода терялись бы, и это было бы неочевидным багом. Поэтому компилятор просто запрещает.
### Почему тогда работает так?

```go
d := Dog{}
d.Speak() // ок!
```

Здесь `d` — переменная, она адресуема, поэтому Go сам превращает вызов в `(&d).Speak()`. Это синтаксический сахар для вызова метода, но он не распространяется на проверку «реализует ли тип интерфейс». Для интерфейсов действует строгое правило method set.
### Ловушки

- **Value receiver с мьютексом** копирует мьютекс при каждом вызове (`go vet` ругается: `copylocks`).
- **Мутация через value receiver** молча не работает, и это частая ошибка новичков.
- **nil-receiver**: у pointer receiver метод можно вызвать на `nil`-указателе, и он не паникует, пока не разыменует его. Иногда это используют намеренно (пустое дерево, `nil`-список).
- **Map хранит значения неадресуемо**: `m["a"].SetName("x")` с pointer receiver не скомпилируется. Храните в map указатели.

**Практическое правило:** если сомневаетесь, берите pointer receiver. Value receiver оставляйте для маленьких иммутабельных типов.
